# Crash and railway audit, November 2026

An audit of starlark-cs against its two robustness policies, run on 2026-11-09 on the .NET 11 code base, before RC1. All
40 confirmed findings are fixed, each with a regression test. Every one of those tests was checked to fail on the old code
before the fix.

## The two policies

**No crash (requirement QA-ROB-001).** No input from a script, a host argument, a file or user text may crash, hang or
exhaust the host. The worst failures are the ones .NET cannot catch: a stack overflow, an out-of-memory error from one huge
allocation, or an exception on a worker thread, each of which kills the process. Infinite loops and unbounded growth count
too.

**Railway-oriented errors.** An expected failure travels on one track to one place that handles it. At the boundary between
a script and its host, the library promises exactly four exception types:

| Exception | Meaning |
|---|---|
| `StarlarkSyntaxException` | The source does not parse. |
| `StarlarkException` | A runtime error, including an unresolved name and a failing host function. |
| `ExecutionLimitException` | A budget ran out: steps, time, memory, or a futures limit. |
| `OperationCanceledException` | The host cancelled the run. |

Any other exception type reaching a host from script input breaks the rule. So does an exception used for ordinary control
flow, an error swallowed or turned into success, or the same failure reported in two different shapes.

**Host programming errors are a different track.** A mistake in the host's own C# code, made before any script runs, is
reported to the host programmer straight away and does not travel on the script track. An example is exposing a class with
two overloads of one method. In .NET these failures are `ArgumentException` and its relatives, and they depend only on the
host's code, never on a script, so they show up the first time the code runs in development. This audit moved several
checks from script time to `Expose` time for exactly that reason. Before, a script calling such a member got an
`InvalidOperationException`, which broke the railway rule.

## How the audit was run

1. **Five auditors** each covered one area and looked for both policies. The areas were: syntax (lexer, parser,
   diagnostics); values and builtins; the interpreter and type checker; futures and interop; and everything outside the
   library (the sample apps, the BASIC interpreter scripts, the playground and the tools). Each auditor read the code and,
   where it could, reproduced the problem with a probe program.
2. **One independent checker per finding** tried to refute it from the code, defaulting to "not real" when the evidence did
   not hold up, and refined the proposed fix.
3. **Three fix agents** worked in separate git worktrees on separate files. For each finding they wrote a regression test,
   confirmed that it failed on the old code, fixed the code, and confirmed that the test passed.
4. The branches were merged and every test suite, the traceability check and the browser site check were run on the result.

One operational lesson: a checker's probe reproduced an unbounded-growth finding exactly as intended and reached 21 GB
before it was killed. Every probe and test run after that ran with a hard heap limit (`DOTNET_GCHeapHardLimit`) and a time
limit.

## The main pattern

Most of the blockers come from a single blind spot. **Budgets were checked only between steps.** The step budget, `Timeout`
and `Cancellation` are enforced when a step is counted, and many single operations did unbounded work inside one step:
`all(range(1 << 60))`, `rsplit` on a large string, walking a tuple that shares its children (2^60 visits for a 60-level
chain), converting an endless host `IEnumerable`, and the static type checker, which had no budget at all. The fix applies
one rule everywhere: **any single operation whose work depends on its input either runs in linear time or counts steps as it
goes**, so the same budgets stop it.

The second pattern is **recursion with no stack guard** in code the earlier rounds had not reached: printing and matching
types, and chains of `load()`. These are now guarded, and the load chain is capped.

## Findings and fixes

Each test name is in the class shown. Every confirmed finding is fixed.

### Blockers (18)

| ID | Problem | Fix | Test |
|---|---|---|---|
| C1 | An `asFuture` host result that is an endless `IEnumerable` kept converting on a pool thread after the run ended, until out of memory. | The conversion gets the run's cancellation token, deadline, remaining steps and memory cap, and stops with the run. | `AuditInteropTests.EndlessAsFutureSequenceStopsWhenTheRunEnds`, `...IsStoppedByTheStepBudget` |
| C2 | A host function returning an endless `IEnumerable` hung the script; `Timeout` and `Cancellation` were ignored. | Each element converted counts one step, plus a size cap against `MaxAllocatedBytes`. | `AuditInteropTests.EndlessHostSequenceIsStoppedByTheStepBudget`, `...ByTheTimeout`, `...ByCancellation`, `EndlessHostDictionaryIsStoppedByTheStepBudget` |
| C3 | BASIC `ON...GOSUB` never checked the 400-entry return stack, so it grew without bound. | Checked like `GOSUB`: `?OM ERROR`. | `AuditAppTests.OnGosubChecksTheReturnStackLimit` |
| C4 | The BASIC console host loaded and ran a program file outside any error handling, so a budget overrun killed the process. | All machine calls go through one `Safe` helper: a budget overrun prints `BREAK`, and a script fault prints `?INTERNAL ERROR`. | `AuditAppTests.ProgramFileOverBudgetIsABreakNotACrash` |
| C5 | In BASIC EDIT mode, a character outside the basic plane made the key decoder throw, and nothing caught it. | Keys are UTF-16 units, and the key path goes through `Safe`. | `AuditAppTests.EditModeAcceptsANonBmpCharacter` |
| C6 | Printing a deeply nested runtime type overflowed the stack. | Stack guard in `Ty.Display`; runtime types are capped at 1024 levels and 2^20 parts. | `AuditRegressionTests.PrintingADeepRuntimeTypeIsAnErrorNotAStackOverflow` and 2 more |
| C7 | `isinstance` or an annotation check against a deep type overflowed the stack. | Stack guards in `Ty.Matches` and `Equals`; each type caches its hash, so most unequal comparisons end at once. | `AuditRegressionTests.IsinstanceOfADeepValueAgainstADeepTypeIsAnErrorNotAStackOverflow`, `UnionOfTwoDeepTypesIsAnErrorNotAStackOverflow` |
| C8 | A deep chain of `load()` calls overflowed the stack. | Load chains are limited to 200 modules (`MaxLoadDepth`), or fewer if the stack runs short; the rethrow at every level is replaced by a success flag. | `AuditRegressionTests.ADeepLoadChainIsAnErrorNotAStackOverflow` (on a 1 MB thread) |
| C9 | The type checker's cost grew roughly cubically (3,000 lines took more than 2 minutes), and no budget applied to it. | Inferred types deeper than 16 levels, larger than 4096 parts or with more than 32 union options widen to `typing.Any`; the checker obeys `Timeout` and `Cancellation`. | `AuditRegressionTests.TypecheckingManyRebindingsOfOneVariableIsFast`, `TypecheckingObeysCancellationAndTimeout` |
| C10 | `isinstance` on a value that shares its children took exponential time and ignored `Timeout` (56 s for 28 levels). | `Matches` counts steps and remembers each (container, type) result by reference, so it is linear. | `AuditRegressionTests.IsinstanceOnASharedTupleIsLinear`, `IsinstanceWithTheMemoGivesTheSameAnswers` |
| C11 | f-string format specs took quadratic time: each one searched to the end of the string. | One search that stops at the first `}`, line break or quote. 250,000 specs went from 8.3 s to well under 4 s. | `AuditSyntaxTests.ManyFormatSpecsInOneFStringLexInLinearTime`, `UnclosedFormatSpecIsStillAnError` |
| C12 | `rsplit` was quadratic (`List.Insert(0)`) inside one step, so `Timeout` never fired. | Builds the parts in order and reverses once: linear. | `AuditRegressionTests.RsplitIsLinear` |
| C13 | Freezing, hashing, equality, printing and JSON encoding of a tuple that shares its children took 2^n visits inside one step. | Freezing remembers the tuples it has seen; the other walks count a step per container. | `AuditRegressionTests.FreezingASharedTupleIsLinear`, `WalkingASharedTupleObeysTheBudget` |
| C14 | `all`, `any`, `join` and `bytes(iterable)` iterated without counting steps, so `all(range(1 << 60))` hung past `Timeout`. | One step per element; `bytes` checks a known length up front. | `AuditRegressionTests.HugeIterationsInOneCallCountSteps` |
| C15 | `+` on bytes, tuples and utf16 skipped the memory budget and size ceiling. One case leaked an `OverflowException`; another used gigabytes of memory. | Checked against the memory budget and the 2^30 ceiling. | `AuditRegressionTests.ConcatenationOfBytesTuplesAndUtf16IsBounded`, `ConcatenationWithoutAMemoryLimitStopsAtTheCeiling` |
| C16 | String `+`, `join`, `fail` and `%`-formatting with no memory limit threw `OutOfMemoryException` to the host. | Checked against the string ceiling and the memory budget. | `AuditRegressionTests.FailMessageIsCheckedAgainstTheMemoryLimit`, `PrintLineIsCheckedAgainstTheMemoryLimit` |
| C17 | `list.extend` and `+=` had no size ceiling or memory check. | Checked when the list's storage grows, so appending stays cheap. | `AuditRegressionTests.ListGrowthIsBounded`, `AppendIsBounded` |
| C18 | `json.indent` output was unbounded and could leak `ArgumentOutOfRangeException`. | Each line is checked before it is added. | `AuditRegressionTests.JsonIndentIsCheckedAgainstTheMemoryLimit` |

## Rejected findings (5)

The checker read the code for each of these and found the mechanics real, but no way for a script or user input to reach
them, or behaviour that matches Go.

| ID | Finding | Why rejected | Hardened anyway? |
|---|---|---|---|
| R1 | A stray closing bracket drove the lexer's bracket counter negative, so `LexAll` stopped emitting indentation. | The input does not parse anyway; the parser reports the first `)`. Go's scanner does the same. | **Yes:** the counter is clamped at zero (`AuditSyntaxTests.StrayClosingBracketDoesNotStopIndentation`). |
| R2 | The futures worker loop swallowed exceptions with an empty catch. | `RunTask` already catches everything a script can raise, and only an internal bookkeeping bug could reach the catch. | **Yes:** `RunTask` now always completes its future, with an internal error if needed, so no waiter can block. |
| R3 | The playground's `BasicLoad` and `BasicReset` ran outside the error handling. | No bundled program can fault while loading, and the names come from a fixed list. | **Yes:** both are wrapped; an error is kept and shown with the next output. |
| R4 | `Typecheck` let syntax errors from loaded modules escape. | That is `StarlarkSyntaxException`, a documented type; a loader's own exception is the host's own code. | No. |
| R5 | `sorted()` rethrew with `throw inner;`, losing the stack trace. | No script code runs inside the comparer; the type and message were already correct. | Overtaken by C28's fix. |

## Behaviour changes a host may notice

- **`Expose` throws `ArgumentException`** for a class with overloads, two members sharing a script name, generic methods,
  or methods taking or returning ref structs or pointers. Rename a member with `[Expose("name")]` or mark it `[Hide]`.
- **`[Expose]` and `[Hide]` on a field** are now compile errors.
- **New limits**, all in the Limits table in `docs/DEVIATIONS.md`:

  | Limit | Value |
  |---|---|
  | `load()` chain depth | 200 |
  | Runtime type depth | 1024 levels |
  | Runtime type size | 2^20 parts |
  | Inferred types | widened to `typing.Any` past 16 levels, 4096 parts or 32 union options |
  | List growth and concatenation of bytes, tuples and utf16 | the 2^30 ceiling and the memory budget |
  | Not-found messages | quote at most 64 characters |
  | Error snippets | clipped to 240 characters per line, 4 lines per span |
- **The type checker now obeys `Timeout` and `Cancellation`.** With `TypecheckBeforeExecute`, the check and the run each
  get the full timeout.
- **`Eval(null)` throws `ArgumentNullException`,** and `Eval("")` is a syntax error.
- **Host failure messages now always name the function:** "Host function `name` failed: ...". One existing test was
  updated for this text.

## What this audit does not cover

- **Comment accuracy:** tracked separately in issue #1.
- **Bugs nobody has found yet.** The audit hardens the paths it found. For hosts that run untrusted code, the defence
  against the rest is **worker mode**, being built for RC1: scripts run in a separate process with operating-system memory
  and CPU limits, so even a crash we have not found cannot take the host down.
- **Performance:** a bytecode VM with heap-allocated frames, which would remove the stack-overflow class by construction,
  is designed in `docs/vm-design.md` and tracked in issue #2.
