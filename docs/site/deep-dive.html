1. Why a C# implementation

Starlark has three mature implementations: Go (used by many tools), Java (inside Bazel) and Rust (from Meta). A .NET application that wanted Starlark had to host one of them out of process, or call native code. A native C# implementation changes what an embedding looks like:

Values are CLR objects

A Starlark int is a BigInteger, a string is a string, None is null. Results come back without marshalling, and host data goes in the same way.

Typed host functions

it.Register("add", (int a, int b) => a + b) is the whole binding. Arguments are converted by C# parameter type, defaults are honoured, and the static checker reads the C# signature.

async becomes futures

A host function that returns a Task can hand the script a future, so a script can keep several I/O operations in flight, with a cap the host sets.

One runtime, every platform

The same assemblies run on Windows, Linux and macOS servers, in desktop apps, and, as this page shows, in a browser through WebAssembly.

.NET tooling

The debugger, profilers, NuGet, and the test stack (xUnit, FsCheck, Hedgehog, Stryker.NET mutation testing) all apply directly.

No native code

Nothing to compile per platform, no unsafe interop boundary, and the whole implementation is about 15,700 lines of C# you can read.

2. From text to result

A program goes through four stages. The first two are a port of the Rust implementation's front end, so syntax errors and their positions match it; the last two were written from the specification.

  1. Lexer (Starlark.Syntax/Lexer.cs, RawLexer.cs). Produces tokens, including the INDENT/DEDENT pair Python-style blocks need. It has a progress guard: a lexer that fails to consume a character on an error stops instead of looping, which a fuzzer once found as an infinite loop on f'{:.
  2. Parser (Parser.cs, 1,100 lines). Recursive descent into an immutable syntax tree (Ast.cs); dialect switches decide which constructs are accepted.
  3. Resolver (Starlark.Eval/Resolver.cs). Static name binding, as the specification describes: every name is classified as local, global, predeclared or universal before anything runs, so an undefined name is an error even in code that never executes.
  4. Evaluator (Interpreter.cs). A tree-walking interpreter over the syntax tree.

Try an undefined name inside a function that is never called. The resolver rejects the program before it starts:

def never_called():
    return undefined_function()

print("this line is never reached")

3. Values

There is no boxing layer: values are ordinary CLR objects, and the type of a value is its .NET type.

Starlark.NETNotes
intBigIntegerArbitrary precision. Small results share pre-built boxes, so loop counters do not allocate.
floatdoublePrinted like Go and Rust: the shortest text that round-trips.
stringstringElements are UTF-8 bytes by default (section 8).
bool, Nonebool, null
list, dict, tuple, setStarList, StarDict, StarTuple, StarSetEach has a frozen flag; a dict keeps insertion order.
functionStarFunctionHolds its syntax tree, closure and compiled parameter list.

Freezing. When a module finishes, everything it built is frozen, and mutating a frozen value is an error. That is what makes a loaded module safe to share between threads. Freezing, equality, hashing and repr are all cycle-safe, and recursion through nested containers is guarded by StackGuard, so a list that contains itself prints instead of overflowing the stack:

def make():
    xs = [1, 2]
    xs.append(xs)        # a list that contains itself
    return xs

print(make())

def power_of_three(n):
    big = 1
    for _ in range(n):
        big = big * 3
    return big

print(len(str(power_of_three(200))), "digits")   # ints have arbitrary precision

4. The evaluator

The evaluator walks the syntax tree. Two methods do almost all of the work: ExecStmt for statements, which returns a small Flow value (normal, break, continue, return) instead of throwing for control flow, and EvalExpr for expressions. Each function call gets a Frame holding its locals; the resolver has already decided which names are local, so a lookup never has to search outward through scopes at run time.

Run state lives in an explicit execution context (ExecutionContext.cs): the step counter, deadline, call depth, the set of functions on the stack (for the recursion check), the string mode, the memory budget and the call stack for error traces. None of this is kept in the Interpreter object (which holds the configuration, the cache of loaded modules and the last run's statistics) or in static fields, which is what lets one frozen module be called from many threads, and lets each future task carry its own copy.

Errors carry their location without cost on the happy path. A runtime error is a StarlarkException. As it unwinds, an exception filter (not a catch) records the first source position it passes and each Starlark frame it leaves, so the trace is built during the first pass of exception handling with no rethrowing:

def parse(record):
    return int(record["age"])

def load_all(rows):
    return [parse(r) for r in rows]

load_all([{"age": "41"}, {"age": "forty"}])

5. Budgets and robustness

Starlark's design keeps scripts from touching the outside world. What a script can still do is use time and memory, so every run can carry budgets: MaxSteps (abstract steps, deterministic), Timeout (wall clock), MaxAllocatedBytes (a per-allocation memory cap: the largest single string, list, tuple or bytes one operation may build, not a total) and a CancellationToken. Running out raises ExecutionLimitException, which no script can catch. This page gives every run 20 million steps, 10 seconds and a 256 MB per-allocation cap. Here is a script that wants a billion steps:

def spin():
    total = 0
    for i in range(1000000000):
        total += i
    return total

spin()

No input may crash the host (requirement QA-ROB-001). That is enforced, not hoped for:

  • Seeded fuzzers for the lexer, parser, interpreter, checker and the BASIC machine, run by the normal test suite and for hours by tools/Soak, which runs each round in a child process under a hard heap limit and watches memory and disk.
  • Exhaustive tests: every string up to a few characters over a small alphabet is fed to the lexer, the parser and the BASIC expression evaluator.
  • Guards on every recursive path (nesting depth, call depth, cyclic values), on huge numbers (an int may have at most 220 bits, about 315,000 decimal digits, and parsing and printing big ints is not quadratic), and on memory (the size of each new string, list, tuple or bytes value is checked before it is built).
  • Starlark-Go's limits, adopted: source text may nest at most 1000 levels ("excessive nesting", counted on every recursive path of the parser, which a test checks against the parser's call graph), a left shift count must be below 512, and a repetition must have an int32 count and fewer than 230 elements. The deepest program the parser accepts resolves, runs and type checks on an ordinary 1 MB thread; a chain like 1 + 1 + ... + 1 is not nesting and is evaluated with a loop at any length. Deep recursion can have a dedicated big-stack thread (ScriptStackSize), which takes it to Go's 100,000 calls.

A shift of 511 bits is allowed; 512 is Go's limit and the same error here:

print(len(str(1 << 511)), "digits")
print(1 << 512)

The first five-hour soak found 116 failing rounds and 6 hangs. All were fixed and each has a regression test.

6. Futures: parallelism without nondeterminism

Starlark is single-threaded by design, because shared mutable state is how programs become nondeterministic. This implementation adds parallelism in a form that keeps the language's guarantee: a program gives the same output however its tasks are scheduled.

def collatz_steps(n):
    steps = 0
    for _ in range(10000):
        if n == 1:
            break
        n = n // 2 if n % 2 == 0 else 3 * n + 1
        steps += 1
    return steps

# parallel_map: results always come back in input order.
print(parallel_map(collatz_steps, [27, 97, 871, 6171]))

# spawn / get / all_of for heterogeneous work.
def describe(label, xs):
    return "%s: %d items, max %d" % (label, len(xs), max(xs))

f = spawn(describe, "evens", [2, 4, 6, 8])
g = spawn(describe, "odds", [1, 3, 5])
print(all_of([f, g]))

The rules that make this deterministic were the result of a design review by four specialists (memory model, scheduling, language semantics, resource limits), who found the first draft unsound:

RuleWhy
Arguments are deep-copied, never frozen in place; aliasing between arguments is preserved.Freezing the caller's list would change the caller's program. Copying means a task cannot race with the caller.
A closure over a running function's variables cannot be spawned.Those variables can be rebound while the task runs. The error tells the author to pass the value as an argument.
Tasks cannot spawn or wait.The task graph has depth one, so deadlock is impossible by construction.
Output is buffered per task and joined in program order.Printed text never interleaves.
all_of reports the lowest-index failure.Not whichever task failed first in time.
Each task gets a fixed slice of the step budget.Which task runs out does not depend on timing.
A future that is never collected is an error.Silently cancelled work hides bugs.

Isolation is visible from the script. The task appends to its own copy; the caller's list is unchanged:

def grow(xs):
    xs.append("added by the task")
    return len(xs)

def run():
    mine = ["a", "b"]
    f = spawn(grow, mine)
    mine.append("added by the caller")
    return [f.get(), mine]

print(run())

Host operations as futures. In C#, a function that returns a Task can be registered with asFuture: true. The script then gets a future at once and can start several operations before waiting on any; FutureLimits.MaxHostOperations caps how many are in flight. The ParallelBuilds sample uses this to run three simulated builds side by side.

In the browser. WebAssembly here has no threads, so tasks run inline on the page's thread at the moment they are started. The test suite runs every futures example both ways and checks that output and errors are identical; only the wall-clock overlap is lost. Two things make that hold: a task's call depth is capped (100 calls, counting the spawner's) in both modes, so deep recursion fails the same way whichever stack it runs on; and once a task hits a limit, every later spawn, get and all_of reports that limit, rather than whatever the scheduler happened to cancel.

7. Types and the static checker

With the types dialect, functions carry annotations that are checked at call time, and record, enum and struct give named data:

Size = enum("S", "M", "L")
Order = record(item = str, size = Size, qty = field(int, 1))

def price(o: Order) -> int:
    base = {"S": 3, "M": 4, "L": 5}[o.size.value]
    return base * o.qty

print(price(Order(item = "tea", size = Size("L"), qty = 2)))
print(price(Order(item = "tea", size = Size("S"))))
print(price("not an order"))

The static checker (TypeCheck/TypeChecker.cs) infers types without running anything, so it finds the error in a branch that only runs on the first of the month. It knows the built-ins, the bundled packages and the C# signatures of host functions. This example is checked, not run:

def label(n: int) -> str:
    if n > 1000000:
        return n          # wrong type, in a branch tests may never reach
    return "small"

def total(xs: list[int]) -> int:
    t = 0
    for x in xs:
        t += x
    return t

total(["1", "2"])

The checker and the runtime are kept in agreement by property tests that generate programs, check them, run them, and require that a program the checker accepts never fails with a type error at run time.

8. Strings

The specification lets an implementation choose 8-bit or 16-bit string elements. This one defaults to UTF-8 bytes, as Go and Rust do, so offsets agree with them. .NET strings are UTF-16 inside, so the interpreter converts offsets on demand and caches the conversion; slicing in the middle of a multi-byte character is an error rather than producing a broken string. A host can choose UTF-16 elements instead (the BASIC machine does, because BASIC counts characters).

s = "naïve café 😀"
chars = list(s.codepoints())
print(len(s), "bytes,", len(chars), "characters")
print(chars[-1], "is code point", ord(chars[-1]))
print(s[0:2], "is 'na'; s[0:3] would cut the two-byte 'ï' in half:")
print(s[0:3])

9. The standard library

Beyond the specification's built-ins, the library adds a json module, the Go compatibility surface (chr, ord, codepoints, module), native elementary math (sin to isinf, backed by System.Math) and two packages written in Starlark itself: std/approx_math.star (the same math from series, identical on every platform) and std/queue.star (a first-in first-out queue with constant amortized time).

load("std/approx_math.star", star_sin = "sin", star_sqrt = "sqrt")
load("std/queue.star", "queue", "enqueue", "dequeue", "queue_len")

print(sin(1.0), star_sin(1.0))      # native, then pure Starlark
print(sqrt(2.0), star_sqrt(2.0))
print(floor(-2.5), ceil(-2.5), round(2.5), round(3.5))

q = queue(["first", "second"])
enqueue(q, "third")
print(dequeue(q), queue_len(q))
print(json.encode_indent({"ok": True, "items": [1, 2]}))

10. A BASIC interpreter written in Starlark

The largest program in the repository is a TRS-80 Level II BASIC interpreter written in Starlark: about 2,600 lines of code and 1,000 lines of comments across six files. It tokenizes like the real machine (keywords are found anywhere, so FORI=1TO10 works), compiles expressions to reverse Polish notation with a shunting-yard parser, emulates single and double precision, keeps a 16 by 64 screen as video memory, and implements the real key-by-key EDIT command. Starlark has no while and no recursion, so the interpreter runs as one flat, bounded loop over a single state dictionary, and the host gives it a slice of statements at a time. 12. Performance


A tree-walking interpreter is not the fastest design, and this one favours clarity and safety checks. Typical numbers
from bench/Starlark.Profile on a desktop machine:




WorkloadTime per run


90,000 iterations of nested integer loopsabout 20 ms


60,000 small function callsabout 30 ms


6,000 string building and formatting roundsabout 13 ms


Parsing a 1,000-line fileabout 1 ms




Two optimisations come from profiling: small integers share pre-built boxes (the loop workload allocates 41% less), and
sorted on large lists of plain numbers or strings uses a parallel merge sort that gives exactly the same order as
